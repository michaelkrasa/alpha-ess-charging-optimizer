# EMHASS comparison protocol — fixed before household financial evaluation

Use the actual EMHASS0.18.6 `perform_naive_mpc_optim` implementation. Compare the current two-window rolling candidate search with EMHASS rolling MPC using identical forecasts first, then evaluate the package's forecasting and identification tools. Continuous arbitrary-power EMHASS output is a reference, not proof of executable savings. The AlphaESS model must include fixed8.6kW charging clipped at fullSOC, automatic PV capture, permission-only household discharge,10%reserve and no battery export. No software grid-import cap. Derived nonbinding solver bounds must never remove a physically possible grid flow.

Both controllers receive only completed-day demand history and weather forecasts available with a six-hour release lag. Tomorrow's published prices become available at15:00 Prague. They replan each15minutes with their own current simulated SOC. Use the same queued next-quarter timing and same executable standard-API mapping, including midnight boundary handling. Live comparison has one device writer and a read-only shadow planner.

EV is grid-only. Keep actual total site load in billing; exclude likely EV sessions from household demand training and prevent simulated battery discharge during them. The API charger meter is unconnected and returnszero. Before financial scoring, the primary inference was corrected to allow concurrent battery charging: a sustained5.5–12kW step, no battery discharge and no SOC decline. The stricter idle-battery/flat-SOC interpretation remains a sensitivity. Forecast inputs rebuild the newest11hours using only samples before their issue time; completed-session retrospective labels are reserved for outcome scoring and uncertainty checks. Never present imputed household demand during EV as measured truth. Validate the inference against independent raw API samples and maintain actual measured site energy.

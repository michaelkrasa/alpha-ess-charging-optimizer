# Household backtest methodology audit

Audited 20 October 2026. Read-only inspection: no device commands were issued. This note describes evidence and evaluation requirements, not verified savings.

## What the existing data supports

Direct CSV inspection found **105,186 household power samples across all 365 days of 2025**, predominantly five-minute snapshots (86,897 consecutive differences are exactly 300 seconds). Powers include PV, load, import and export, plus battery SOC. The fetching script converts API watts into kW; timestamps have no UTC offset. There are no duplicate timestamp strings, but that does not establish unique real instants across DST. Daily energy history has 2,036 records from 2021-01-01 through 2026-07-29. These are the files already available before any new API fetch. Sources: [power CSV](output/alphaess_power_2025.csv), [daily CSV](output/alphaess_daily_history.csv), [power ingestion](fetch_alphaess_power_history.py), [daily ingestion](fetch_alphaess_history.py).

The OTE CSV has **15,363 records across 364 days**; 2025-07-04 is missing. It has hourly prices before October and quarter-hour prices thereafter. Do not interpolate the missing day's price to claim an observed-cost result. Expand an hourly published price over its four constituent quarter hours, retaining original resolution metadata. Source: [OTE CSV](output/ote_prices_2025.csv), [OTE ingestion](fetch_ote_history.py).

Basic energy reconciliation is encouraging but imperfect. Across days with more than 1 kWh, the median ratio of five-minute-snapshot integration to API daily totals is 1.001 for PV, 1.023 for reconstructed household load, 1.007 for import and 1.011 for export. Load ratios' 10th–90th percentile span is 0.992–1.105. These are sampling-quality diagnostics, using equal five-minute weights, not calibrated meter totals. The rigorous evaluation should use elapsed-time integration and report exclusions and reconciliation error.

Historical load is **AlphaESS-observed load**, not independently proven non-EV demand. The prior analysis explicitly describes 2025 as a one-EV year, while the API's charging-pile field is zero throughout this CSV. Do not remove load spikes using an arbitrary cap or claim EV energy has been subtracted without a separate measured channel. The user has excluded EV control; we still need a clear measurement boundary for any load the ESS cannot supply. Sources: [prior household analysis](solar_battery_plan.md), [power CSV](output/alphaess_power_2025.csv), [previous capped-load method](model_czech_market_system.py:58).

## Why the current replay is insufficient

The existing replay feeds **actual future load and solar** into one daily optimization, hard-codes 17.2 kWh capacity, and raises initial SOC to reserve. It is already labelled hindsight in its output. It does not execute a rolling simulated battery against unknown future demand and does not compute comparative realized bills. Source: [replay](../src/manager/replay.py:20).

The previous sizing optimizer is also not a controller comparison: it uses a full-year horizon, altered load, synthetic PV, flexible weekly EV charging and interpolated missing prices. Its year-end SOC constraint is useful, but its cost results cannot establish savings for the new household-only controller. Source: [sizing model](model_czech_market_system.py:42).

The new optimizer chooses separate continuous grid-charge, solar-charge and household-discharge flows. Export is confined to surplus PV, and a binary mode prevents simultaneous battery charge and discharge. However, `AlphaDevice.apply` maps both `solar` and `self_consume` to **native operation**, without imposing the optimized solar/discharge power. Native operation should therefore be simulated as greedy PV storage and household discharge within limits, not as exact execution of every optimized kW. `hold` uses a scheduled charging period with a reserve target and 100 W setting; its physical semantics remain unverified. The adapter also rounds charge targets down to integer percentages, imposes minimum charge power, and falls back to native at midnight/DST boundaries. Sources: [optimizer](../src/manager/planner.py:60), [action selection](../src/manager/planner.py:129), [adapter](../src/manager/device.py:228).

Report at least two variants: **ideal optimized flows** (mathematical opportunity) and **device-action simulation** (native behavior, rounded targets and power limits). A simulation that assumes successful hold is conditional on that capability. With device permission currently blocked, neither variant proves actual hardware behavior. Source: [commissioning status](../README.md:75).

## Credible walk-forward evaluation

1. Use contiguous UTC quarter hours and at least seven completed historical days for warm-up. At each decision, train forecasts only on earlier completed days; do not build a full-year typical profile or normalize months using future totals. Recalculate every 15 minutes and carry simulated SOC continuously. The deployed load predictor uses raw historical samples' median per local quarter-hour, which differs slightly from a median of seven daily quarter-hour means. Sources: [load forecast](../src/manager/providers.py:160), [UTC intervals](../src/manager/domain.py:16).
2. Make tomorrow's prices visible only after the configured 15:00 Europe/Prague publication boundary. Price history fetched today must not be treated as already known at earlier decision times. Run from the same decision-to-next-boundary timing as production. If skipping a day for missing data, split the continuous experiment, restart all strategies from the same SOC, and disclose lost evaluation days. Source: [production price horizon](../src/manager/providers.py:271).
3. Simulate the selected action on actual subsequent household load and PV, clipping by actual surplus/deficit, SOC, efficiencies, charge/discharge limits and connection headroom. Preserve energy conservation; battery export must remain zero. Report reserve violations, import-limit exceedances originating in household load, turnover and forecast errors alongside EUR costs.
4. Compare on identical data against native self-consumption (no grid charging), and optionally the legacy two-window policy. Keep the historical observed import/export bill separate: its battery condition, user settings and actions were not assigned experimentally. Assess both cash electricity cost and electricity cost plus assumed battery wear; wear is a model assumption, not an invoice payment. Sources: [settings](../src/manager/settings.py), [legacy battery policy](../src/battery_manager.py).
5. Give all strategies identical initial energy. Report raw ending SOC and both unadjusted and common-price terminal-energy-adjusted cost. Use one prespecified residual value or identical endpoint constraints; do not let one strategy's unused battery energy disappear. Never reset SOC independently each day or increase recorded energy to reserve without charging for it. The deployed optimizer's terminal-value heuristic is part of its policy, not a fair-scoring rule. Source: [terminal heuristic](../src/manager/planner.py:93).
6. Treat current invoice-based tariff coefficients applied to 2025 as a **current-tariff scenario on historical consumption**, not reconstructed 2025 billing. The only verified HDO schedule is dated 20–26 October 2026; it cannot prove historical switching periods. Publish high/low tariff sensitivity or an explicit assumed schedule. Use an FX rate known at decision time (previous published fixing before daily release), or a fixed declared scenario conversion. Source: [tariff formula](../src/manager/tariff.py), [schedule validity](../manager.yaml).

On 2025-03-30 the power CSV has 276 samples; on 2025-10-26 it has 300 and 23 samples labelled in the 02:00 hour. Sorting offsetless strings cannot recover fold reliably. The existing replay assigns `Europe/Prague` with default fold=0, so repeated-hour measurements merge. Exclude DST-transition days unless original API order or offset-bearing timestamps resolve each real instant; check missing quarter-hours separately. Source: [replay timestamp handling](../src/manager/replay.py:25).

## Historical solar forecasts: feasible, with qualifications

Open-Meteo's Historical Forecast endpoint stitches early portions of successive runs; using those values for future intervals would expose newer information than a historical decision had. Previous Runs provides fixed 1–7 day lead times, useful for skill evaluation but not the original complete horizon from a decision's model run. Sources: [Historical Forecast documentation](https://open-meteo.com/en/docs/historical-forecast-api), [Previous Runs documentation](https://open-meteo.com/en/docs/previous-runs-api).

The **Single Runs API** provides full forecasts selected by initialization time. ECMWF IFS HRES archives extend back to March 2024; most other model archives start April 2026. GTI is supported with tilt/azimuth. Initialization is not publication: global forecasts typically arrive 4–6 hours later. Select an initialization at least six hours before the historical decision, and disclose that availability-lag assumption. A read-only probe for `models=ecmwf_ifs`, `run=2025-12-10T00:00`, GTI, three days, returned 72 hours (71 non-null). Calibration must use only past household production. This is an **archived IFS forecast variant**, not an exact replay of today's automatically selected `best_match` provider. Source: [Single Runs documentation](https://open-meteo.com/en/docs/single-runs-api).

Single Runs and Previous Runs are currently accessible on Open-Meteo's free noncommercial tier, within published request limits. Cache results locally and attribute the weather source. Source: [Open-Meteo pricing](https://open-meteo.com/en/pricing).

Actual archive collection subsequently fetched **1,674 of 1,692 requested six-hourly IFS runs** into ignored `data/backtests/weather/`: 1,446 runs for 2024-12-31 through 2025-12-31, and all 228 runs for 2026-08-24 through 2026-10-19. Every successful payload contains 72 hourly timestamps, with GTI null at initialization and 71 non-null values thereafter. Eighteen 2025 runs between 4 August 18:00 and 9 August 12:00 UTC were unavailable (HTTP 400) or had entirely null GTI. The manifest records every failure; no forecasts were fabricated. Never fill an archive gap using a later run that was unavailable at the decision. Source: ignored `data/backtests/weather/fetch_manifest.json` and the timestamped original API payloads. GTI at a timestamp represents the **preceding** hour; align it to that delivery interval when building quarter-hour forecasts.

A seven-day same-time solar persistence forecast is a defensible, entirely causal fallback and useful stress benchmark. It differs materially from the deployed weather-based PV forecast, so label it explicitly; it cannot validate that forecast's accuracy or establish a strict lower bound on its savings. The live PV method calibrates using yesterday's production against recent irradiance and multiplies the predicted result by 0.8. Source: [live PV forecast](../src/manager/providers.py:195).
